# 메모리 환경 조사

날짜: 2026-03-17

이 문서는 작업 `PAP-530`에서 참조된 메모리 시스템을 요약하고 Paperclip에 중요한 설계 패턴을 추출합니다.

## 이 조사에서 Paperclip이 필요로 하는 것

Paperclip은 단일 독단적 메모리 엔진이 되려고 하지 않습니다. 더 유용한 목표는 다음과 같은 컨트롤 플레인 메모리 표면입니다:

- 회사 범위를 유지
- 각 회사가 기본 메모리 프로바이더를 선택할 수 있게 함
- 특정 에이전트가 그 기본값을 재정의할 수 있게 함
- Paperclip 실행, 이슈, 댓글, 문서에 대한 출처 추적을 유지
- 메모리 관련 비용과 지연 시간을 컨트롤 플레인의 다른 작업 기록과 동일하게 기록
- 내장 기능뿐만 아니라 플러그인 제공 프로바이더와 함께 동작

질문은 "어떤 메모리 프로젝트가 이기는가?"가 아닙니다. 질문은 "유용한 차이를 평탄화하지 않으면서 매우 다른 여러 메모리 시스템 위에 놓일 수 있는 가장 작은 Paperclip 계약은 무엇인가?"입니다.

## 간략한 분류

### 호스팅 메모리 API

- `mem0`
- `supermemory`
- `Memori`

이들은 간단한 애플리케이션 통합 스토리에 최적화되어 있습니다: 대화/콘텐츠와 신원을 보내고, 나중에 관련 메모리 또는 사용자 컨텍스트를 쿼리합니다.

### 에이전트 중심 메모리 프레임워크 / 메모리 OS

- `MemOS`
- `memU`
- `EverMemOS`
- `OpenViking`

이들은 메모리를 검색 인덱스뿐만 아니라 에이전트 런타임 하위 시스템으로 취급합니다. 일반적으로 작업 메모리, 프로필, 파일 시스템 스타일 구성, 비동기 수집, 스킬/리소스 관리를 추가합니다.

### 로컬 우선 메모리 저장소 / 인덱스

- `nuggets`
- `memsearch`

이들은 로컬 영속성, 검사 가능성, 낮은 운영 오버헤드를 강조합니다. Paperclip이 현재 로컬 우선이며 최소한 하나의 설정 불요 경로가 필요하기 때문에 유용합니다.

## 프로젝트별 노트

| 프로젝트 | 형태 | 주요 API / 모델 | Paperclip과의 적합성 | 주요 불일치 |
|---|---|---|---|---|
| [nuggets](https://github.com/NeoVertex1/nuggets) | 로컬 메모리 엔진 + 메시징 게이트웨이 | 토픽 범위 HRR 메모리, `remember`, `recall`, `forget`, `MEMORY.md`로의 팩트 승격 | 경량 로컬 메모리와 자동 승격의 좋은 예시 | 매우 특정한 아키텍처; 범용 멀티테넌트 서비스 아님 |
| [mem0](https://github.com/mem0ai/mem0) | 호스팅 + OSS SDK | `add`, `search`, `getAll`, `get`, `update`, `delete`, `deleteAll`; `user_id`, `agent_id`, `run_id`, `app_id`를 통한 엔티티 파티셔닝 | 신원과 메타데이터 필터가 있는 깔끔한 프로바이더 API에 가장 근접 | 프로바이더가 추출을 크게 좌우; Paperclip은 모든 백엔드가 mem0처럼 동작한다고 가정해서는 안 됨 |
| [MemOS](https://github.com/MemTensor/MemOS) | 메모리 OS / 프레임워크 | 통합 추가-검색-편집-삭제, 메모리 큐브, 멀티모달 메모리, 도구 메모리, 비동기 스케줄러, 피드백/수정 | 단순 검색을 넘어선 선택적 기능의 강력한 소스 | Paperclip이 처음에 표준화해야 할 최소 계약보다 훨씬 광범위 |
| [supermemory](https://github.com/supermemoryai/supermemory) | 호스팅 메모리 + 컨텍스트 API | `add`, `profile`, `search.memories`, `search.documents`, 문서 업로드, 설정; 자동 프로필 구축 및 삭제 | 원시 검색 결과가 아닌 "컨텍스트 번들"의 강력한 예시 | 자체 온톨로지와 호스팅 플로우를 중심으로 크게 제품화됨 |
| [memU](https://github.com/NevaMind-AI/memU) | 능동적 에이전트 메모리 프레임워크 | 파일 시스템 메타포, 능동적 루프, 의도 예측, 상시 가동 컴패니언 모델 | 메모리가 단순 검색이 아닌 에이전트 행동을 트리거해야 할 때의 좋은 소스 | 능동적 어시스턴트 프레이밍이 Paperclip의 작업 중심 컨트롤 플레인보다 광범위 |
| [Memori](https://github.com/MemoriLabs/Memori) | 호스팅 메모리 패브릭 + SDK 래퍼 | LLM SDK에 대해 등록, `entity_id` + `process_id`를 통한 어트리뷰션, 세션, 클라우드 + BYODB | 모델 클라이언트 주변 자동 캡처의 강력한 예시 | 래퍼 중심 설계가 Paperclip의 실행 / 이슈 / 댓글 생명주기에 1:1 매핑되지 않음 |
| [EverMemOS](https://github.com/EverMind-AI/EverMemOS) | 대화형 장기 메모리 시스템 | MemCell 추출, 구조화된 내러티브, 사용자 프로필, 하이브리드 검색 / 재순위 | 출처가 풍부한 구조화된 메모리와 진화하는 프로필의 유용한 모델 | 일반화된 컨트롤 플레인 이벤트보다 대화 메모리에 집중 |
| [memsearch](https://github.com/zilliztech/memsearch) | markdown 우선 로컬 메모리 인덱스 | markdown을 정보의 원천으로, `index`, `search`, `watch`, 트랜스크립트 파싱, 플러그인 훅 | 로컬 내장 프로바이더와 검사 가능한 출처를 위한 훌륭한 기준선 | 의도적으로 단순; 호스팅 서비스 시맨틱이나 풍부한 수정 워크플로 없음 |
| [OpenViking](https://github.com/volcengine/OpenViking) | 컨텍스트 데이터베이스 | 메모리/리소스/스킬의 파일 시스템 스타일 구성, 계층적 로딩, 시각화된 검색 궤적 | 탐색/검사 UX와 컨텍스트 출처를 위한 강력한 소스 | "컨텍스트 데이터베이스"를 Paperclip이 소유해야 할 것보다 더 큰 제품 표면으로 취급 |

## 환경 전반의 공통 프리미티브

시스템들이 아키텍처에서 의견이 다르지만, 몇 가지 프리미티브에서 수렴합니다:

- `ingest`: 텍스트, 메시지, 문서, 트랜스크립트에서 메모리 추가
- `query`: 작업, 질문, 범위를 기반으로 메모리 검색 또는 조회
- `scope`: 사용자, 에이전트, 프로젝트, 프로세스, 세션별 메모리 파티셔닝
- `provenance`: 메모리가 어디에서 왔는지 설명할 충분한 메타데이터 전달
- `maintenance`: 시간에 따른 메모리 업데이트, 삭제, 중복 제거, 압축, 수정
- `context assembly`: 원시 메모리를 에이전트를 위한 프롬프트 준비 번들로 변환

Paperclip이 이러한 것들을 노출하지 않으면 위의 시스템들에 잘 적응하지 못할 것입니다.

## 시스템 간 차이점

이러한 차이점이 정확히 Paperclip이 단일 하드코딩된 엔진 대신 계층화된 계약이 필요한 이유입니다.

### 1. 누가 추출을 소유하는가?

- `mem0`, `supermemory`, `Memori`는 프로바이더가 대화에서 메모리를 추론할 것으로 기대합니다.
- `memsearch`는 호스트가 어떤 markdown을 작성할지 결정한 후 인덱싱하도록 기대합니다.
- `MemOS`, `memU`, `EverMemOS`, `OpenViking`은 그 사이 어딘가에 위치하며 종종 더 풍부한 메모리 구축 파이프라인을 노출합니다.

Paperclip은 둘 다 지원해야 합니다:

- 프로바이더 관리 추출
- Paperclip 관리 추출 + 프로바이더 관리 저장 / 검색

### 2. 정보의 원천은 무엇인가?

- `memsearch`와 `nuggets`는 디스크에서 원천을 검사 가능하게 만듭니다.
- 호스팅 API는 종종 프로바이더 저장소를 정본으로 만듭니다.
- `OpenViking`과 `memU` 같은 파일 시스템 스타일 시스템은 계층 구조 자체를 메모리 모델의 일부로 취급합니다.

Paperclip은 단일 저장소 형태를 요구해서는 안 됩니다. Paperclip 엔티티로의 정규화된 참조를 요구해야 합니다.

### 3. 메모리는 단순 검색인가, 아니면 프로필과 계획 상태까지 포함하는가?

- `mem0`와 `memsearch`는 검색과 CRUD를 중심으로 합니다.
- `supermemory`는 사용자 프로필을 일급 출력으로 추가합니다.
- `MemOS`, `memU`, `EverMemOS`, `OpenViking`은 도구 추적, 작업 메모리, 리소스, 스킬로 확장합니다.

Paperclip은 일반 검색을 최소 계약으로 만들고 더 풍부한 출력은 선택적 기능으로 해야 합니다.

### 4. 메모리는 동기식인가 비동기식인가?

- 로컬 도구는 종종 프로세스 내에서 동기적으로 작동합니다.
- 대규모 시스템은 스케줄러, 백그라운드 인덱싱, 압축, 동기화 작업을 추가합니다.

Paperclip은 직접 요청/응답 작업과 백그라운드 유지보수 훅 모두 필요합니다.

## Paperclip 관련 시사점

### Paperclip이 소유해야 할 관심사

- 프로바이더를 회사에 바인딩하고 선택적으로 에이전트별로 재정의
- Paperclip 엔티티를 프로바이더 범위로 매핑
- 이슈 댓글, 문서, 실행, 활동에 대한 출처 추적
- 메모리 작업에 대한 비용 / 토큰 / 지연 시간 보고
- Paperclip UI의 탐색 및 검사 표면
- 파괴적 작업에 대한 거버넌스

### 프로바이더가 소유해야 할 관심사

- 추출 휴리스틱
- 임베딩 / 인덱싱 전략
- 순위 및 재순위
- 프로필 합성
- 모순 해결 및 삭제 로직
- 저장소 엔진 세부사항

### 컨트롤 플레인 계약은 작게 유지해야 함

Paperclip은 모든 프로바이더의 모든 기능을 표준화할 필요가 없습니다. 필요한 것은:

- 필수 포터블 코어
- 더 풍부한 프로바이더를 위한 선택적 기능 플래그
- 모든 프로바이더가 내부적으로 동일하다고 가장하지 않으면서 프로바이더 네이티브 ID와 메타데이터를 기록하는 방법

## 권장 방향

Paperclip은 2계층 메모리 모델을 채택해야 합니다:

1. `메모리 바인딩 + 컨트롤 플레인 레이어`
   Paperclip이 회사, 에이전트, 프로젝트에 적용되는 프로바이더 키를 결정하고, 모든 메모리 작업을 출처와 사용량과 함께 기록합니다.

2. `프로바이더 어댑터 레이어`
   내장 또는 플러그인 제공 어댑터가 Paperclip 메모리 요청을 프로바이더별 호출로 변환합니다.

포터블 코어가 다뤄야 할 범위:

- ingest / write
- search / recall
- browse / inspect
- 프로바이더 레코드 핸들로 조회
- forget / correction
- 사용량 보고

선택적 기능이 다뤄야 할 범위:

- 프로필 합성
- 비동기 수집
- 멀티모달 콘텐츠
- 도구 / 리소스 / 스킬 메모리
- 프로바이더 네이티브 그래프 탐색

이것으로 다음을 지원하기에 충분합니다:

- `memsearch`와 유사한 로컬 markdown 우선 기준선
- `mem0`, `supermemory`, `Memori`와 유사한 호스팅 서비스
- `MemOS`나 `OpenViking`과 같은 더 풍부한 에이전트 메모리 시스템

Paperclip 자체를 모놀리식 메모리 엔진으로 만들지 않으면서.

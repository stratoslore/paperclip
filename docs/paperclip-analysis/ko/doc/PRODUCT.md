# Paperclip — 제품 정의

## 개요

Paperclip은 자율 AI 회사를 위한 컨트롤 플레인입니다. 하나의 Paperclip 인스턴스로 여러 회사를 운영할 수 있습니다. **회사**는 일등급 객체입니다.

## 핵심 개념

### 회사

회사는 다음을 가집니다:

- **목표** — 존재 이유 ("3개월 내 MRR $1M을 달성하는 최고의 AI 메모 앱 만들기")
- **직원** — 모든 직원은 AI 에이전트
- **조직 구조** — 누가 누구에게 보고하는지
- **수익 및 비용** — 회사 수준에서 추적
- **작업 계층** — 모든 작업은 회사 목표로 추적 가능

### 직원 및 에이전트

모든 직원은 에이전트입니다. 회사를 만들 때 CEO를 정의하는 것부터 시작하여 확장해 나갑니다.

각 직원은 다음을 가집니다:

- **어댑터 유형 + 구성** — 이 에이전트가 어떻게 실행되고 무엇이 정체성/행동을 정의하는지. 이것은 어댑터마다 다릅니다 (예: OpenClaw 에이전트는 SOUL.md와 HEARTBEAT.md 파일을 사용할 수 있고, Claude Code 에이전트는 CLAUDE.md를 사용할 수 있으며, 순수 스크립트는 CLI 인자를 사용할 수 있습니다). Paperclip은 형식을 규정하지 않습니다 — 어댑터가 규정합니다.
- **역할 및 보고** — 직함, 보고 대상, 부하 직원
- **역량 설명** — 이 에이전트가 무엇을 하고 언제 관련이 있는지에 대한 짧은 설명 (다른 에이전트가 누가 무엇을 도울 수 있는지 파악하는 데 도움)

예시: CEO 에이전트의 어댑터 구성은 각 하트비트에서 "임원들이 무엇을 하고 있는지 검토하고, 회사 지표를 확인하고, 필요하면 우선순위를 재조정하고, 새로운 전략적 이니셔티브를 배정하라"고 지시합니다. 엔지니어의 구성은 "배정된 작업을 확인하고, 가장 높은 우선순위를 선택하고, 작업하라"고 지시합니다.

그런 다음 CEO에게 보고하는 사람을 정의합니다: 프로그래머를 관리하는 CTO, 마케팅 팀을 관리하는 CMO 등. 트리의 모든 에이전트가 자체 어댑터 구성을 가집니다.

### 에이전트 실행

에이전트의 하트비트를 실행하는 두 가지 기본 모드가 있습니다:

1. **명령 실행** — Paperclip이 프로세스(셸 명령, Python 스크립트 등)를 시작하고 추적합니다. 하트비트는 "이것을 실행하고 모니터링하라"입니다.
2. **요청 후 잊기** — Paperclip이 외부에서 실행 중인 에이전트에 웹훅/API 호출을 보냅니다. 하트비트는 "이 에이전트에게 깨어나라고 알리라"입니다. (OpenClaw 훅이 이 방식으로 작동합니다.)

합리적인 기본값을 제공합니다 — 구성에 따라 Claude Code 또는 Codex에 셸 아웃하고, 세션 ID를 기억하고, 기본 스크립트를 실행하는 기본 에이전트. 하지만 무엇이든 연결할 수 있습니다.

### 작업 관리

작업 관리는 계층적입니다. 어떤 시점에서든 모든 작업은 상위 작업의 체인을 통해 회사의 최상위 목표로 추적 가능해야 합니다:

```
I am researching the Facebook ads Granola uses (current task)
  because → I need to create Facebook ads for our software (parent)
    because → I need to grow new signups by 100 users (parent)
      because → I need to get revenue to $2,000 this week (parent)
        because → ...
          because → We're building the #1 AI note-taking app to $1M MRR in 3 months
```

작업에는 상위 관계가 있습니다. 모든 작업은 회사 목표까지 이어지는 상위 작업을 위해 존재합니다. 이것이 자율 에이전트를 정렬하는 핵심입니다 — 에이전트는 항상 "내가 왜 이것을 하고 있는지?"에 답할 수 있습니다.

더 상세한 작업 구조는 추후 결정.

## 원칙

1. **에이전트 실행 방식에 대해 비간섭적.** 에이전트는 OpenClaw 봇, Python 스크립트, Node 스크립트, Claude Code 세션, Codex 인스턴스 등 무엇이든 가능합니다. Paperclip은 통신을 위한 컨트롤 플레인을 정의하고 하트비트를 위한 유틸리티 인프라를 제공합니다. 에이전트 런타임을 강제하지 않습니다.

2. **회사가 조직의 단위.** 모든 것은 회사 아래에 있습니다. 하나의 Paperclip 인스턴스, 여러 회사.

3. **어댑터 구성이 에이전트를 정의.** 모든 에이전트는 정체성과 행동을 제어하는 어댑터 유형과 구성을 가집니다. 최소 계약은 "호출 가능하다"입니다.

4. **모든 작업은 목표로 추적.** 계층적 작업 관리는 어떤 것도 고립되어 존재하지 않는다는 것을 의미합니다. 작업이 회사 목표에 왜 중요한지 설명할 수 없다면, 존재해서는 안 됩니다.

5. **컨트롤 플레인이지 실행 플레인이 아님.** Paperclip은 조율합니다. 에이전트는 어디에서든 실행되고 보고합니다.

## 사용자 흐름 (이상적 시나리오)

1. Paperclip을 열고, 새 회사 생성
2. 회사 목표 정의: "3개월 내 MRR $1M을 달성하는 최고의 AI 메모 앱 만들기"
3. CEO 생성
   - 어댑터 선택 (예: Claude Code용 프로세스 어댑터, OpenClaw용 HTTP 어댑터)
   - 어댑터 구성 (에이전트 정체성, 루프 동작, 실행 설정)
   - CEO가 전략적 분해를 제안 → 이사회 승인
4. CEO의 보고자 정의: CTO, CMO, CFO 등
   - 각각 자체 어댑터 구성과 역할 정의를 가짐
5. 그들의 보고자 정의: CTO 아래 엔지니어, CMO 아래 마케터 등
6. 예산 설정, 초기 전략 작업 정의
7. 실행 — 에이전트가 하트비트를 시작하고 회사가 운영됨

## 가이드라인

Paperclip이 지원해야 하는 두 가지 런타임 모드가 있습니다:

- `local_trusted` (기본값): 로그인 마찰 없는 단일 사용자 로컬 신뢰 배포
- `authenticated`: 프라이빗 네트워크와 퍼블릭 배포 노출 정책을 모두 지원하는 로그인 필수 모드

정규 모드 설계 및 명령 기대 사항은 `doc/DEPLOYMENT-MODES.md`에 있습니다.

Paperclip의 핵심 정체성은 **자율 AI 회사를 위한 컨트롤 플레인**으로, **회사, 조직도, 목표, 이슈/댓글, 하트비트, 예산, 승인, 이사회 거버넌스**를 중심으로 합니다. 공개 문서는 현재 경계에 대해서도 명확합니다: **작업/댓글이 내장된 커뮤니케이션 모델**이며, Paperclip은 **챗봇이 아니고**, **코드 리뷰 도구가 아닙니다**. 로드맵은 이미 **더 쉬운 온보딩, 클라우드 에이전트, 더 쉬운 에이전트 구성, 플러그인, 더 나은 문서, ClipMart/ClipHub 스타일의 재사용 가능한 회사/템플릿** 방향을 가리키고 있습니다.

## Paperclip이 해야 할 것과 하지 말아야 할 것

**해야 할 것**

- **이사회 수준과 회사 수준**을 유지. 사용자는 목표, 조직, 예산, 승인, 산출물을 관리해야 합니다.
- 처음 5분을 마법처럼 느끼게: 설치하고, 몇 가지 질문에 답하고, CEO가 실제로 무언가를 하는 것을 봅니다.
- 표면이 대화형으로 느껴지더라도 작업을 **이슈/댓글/프로젝트/목표**에 고정.
- **에이전시 / 내부 팀 / 스타트업**을 다른 템플릿과 라벨을 가진 동일한 기본 추상화로 취급.
- 산출물을 일등급으로: 파일, 문서, 리포트, 미리보기, 링크, 스크린샷.
- **엔지니어링 워크플로우에 대한 훅** 제공: 워크트리, 미리보기 서버, PR 링크, 외부 리뷰 도구.
- 풍부한 채팅, 지식 베이스, 문서 에디터, 커스텀 트레이싱 등 엣지 케이스에 **플러그인** 사용.

**하지 말아야 할 것**

- 핵심 제품을 범용 채팅 앱으로 만들지 마세요. 현재 제품 정의는 명시적으로 작업/댓글 중심이며 "챗봇이 아니"라고 하며, 그 경계는 가치가 있습니다.
- 완전한 Jira/GitHub 대체품을 만들지 마세요. 저장소/문서는 이미 Paperclip을 풀 리퀘스트 리뷰가 아닌 조직 오케스트레이션으로 포지셔닝하고 있습니다.
- 엔터프라이즈급 RBAC를 먼저 구축하지 마세요. 현재 V1 스펙은 여전히 다중 보드 거버넌스와 세분화된 인간 권한을 범위 밖으로 취급하므로, 첫 다중 사용자 버전은 대략적이고 회사 범위여야 합니다.
- 원시 bash 로그와 트랜스크립트를 앞세우지 마세요. 기본 뷰는 사람이 읽을 수 있는 의도/진행 상황이어야 하며, 원시 세부 사항은 그 아래에 있어야 합니다.
- 절대 필요하지 않는 한 사용자에게 프로바이더/API 키 설정을 이해하도록 강요하지 마세요. 이미 활성화된 온보딩/인증 이슈가 있으며, 여기서의 마찰은 분명히 실재합니다.

## 구체적 설계 목표

1. **첫 성공까지 5분 이내**
   새로운 사용자는 설치부터 "CEO가 첫 작업을 완료했다"까지 한 번의 세션에서 도달해야 합니다.

2. **이사회 수준의 추상화가 항상 우선**
   기본 UI는 다음에 답해야 합니다: 회사가 무엇을 하고 있는지, 누가 하고 있는지, 왜 중요한지, 비용이 얼마인지, 승인이 필요한 것은 무엇인지.

3. **대화는 작업 객체에 연결**
   "CEO와 대화"는 여전히 전략 스레드, 의사 결정, 작업, 또는 승인으로 귀결되어야 합니다.

4. **점진적 공개**
   최상위 레이어: 사람이 읽을 수 있는 요약. 중간 레이어: 체크리스트/단계/아티팩트. 최하위 레이어: 원시 로그/도구 호출/트랜스크립트.

5. **산출물 우선**
   사용자가 결과를 볼 수 있을 때까지 작업은 완료된 것이 아닙니다: 파일, 문서, 미리보기 링크, 스크린샷, 계획, 또는 PR.

6. **로컬 우선, 클라우드 준비**
   로컬 단독 사용과 공유/프라이빗 또는 퍼블릭/클라우드 배포 간에 멘탈 모델이 변하지 않아야 합니다.

7. **안전한 자율성**
   자동 모드는 허용됩니다; 숨겨진 토큰 소모는 허용되지 않습니다.

8. **얇은 코어, 풍부한 엣지**
   선택적 채팅, 지식, 특수 인터페이스는 컨트롤 플레인을 비대화하지 않고 플러그인/확장 기능에 넣으세요.
